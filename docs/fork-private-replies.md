# 私密回复与 Docker 发布

本 fork 的开发分支为 `dev`，远端 `main` 与上游对齐。MySQL 支持私密回复及直接发给博主的顶层私密留言；不会根据历史评论的邮箱或昵称自动认领账户。

## 可见性与交互

- 登录访客可以创建顶层私密留言，接收人为唯一管理员；多个管理员时必须通过 `PRIVATE_MESSAGE_ADMIN_ID` 指定博主账户 ID。接收人由服务端确定，不能由客户端指定。博主不能向自己创建私密留言。

- 登录账户回复另一个账户的公开评论时，可以勾选「私密回复」。匿名历史评论不能作为私密回复对象。
- 双方由服务端保存的账户 ID 确定，客户端不能指定身份。后续回复继承原来的两位参与者，不能转为公开或加入第三人。
- 双方和管理员可以查看；管理员可以审核、编辑、删除，但不能作为第三人加入对话。
- 作者可以编辑自己的正文。公开／私密属性、所属文章、父评论、作者和参与者在创建后不可通过编辑 API 改写。
- 评论列表、最近评论、计数先在 SQL 查询中限制可见范围，再进行排序和分页。RSS、排行榜、等级统计只使用公开评论。
- 切换账户或退出登录时清空当前评论列表和回复状态，丢弃旧请求。私密草稿仅存在内存，取消或刷新后不会保留；普通公开草稿仍按原方式保存。
- 私密回复不调用 Akismet、评论保存／修改 hooks、邮件、即时通知或 webhook。私密输入框禁用内置外部图片上传和 GIF 搜索。

这是服务端访问控制，不是端到端加密。数据库、服务器和管理员备份持有者仍能读取正文。手动插入的外部图片或附件链接不因此变成私有资源。

已有 `[private]` 文本标记不会被自动处理，历史评论仍保留原状态。数据库导出仅限管理员，包含私密记录；在线导入会拒绝私密记录，以免重新分配 ID 后错误绑定参与者。恢复此类备份需要保留账户和评论 ID 的离线操作。

## 数据库迁移

先备份数据库，在维护窗口执行一次 `assets/migrations/001-private-replies.mysql.sql`，再启动此 fork。默认表名是 `wl_Comment`，如实际前缀不同需修改 SQL。迁移只增加以下字段，已有记录默认 `public`：

| 字段             | 用途                 |
| ---------------- | -------------------- |
| `visibility`     | `public` / `private` |
| `private_user_a` | 第一位参与者账户 ID  |
| `private_user_b` | 第二位参与者账户 ID  |

不要对已有数据库运行 `assets/waline.sql`：那是包含删除表语句的初始化文件。本版本尚未操作线上数据库。

写入私密记录以后，不能直接换回忽略这些字段的官方服务端，否则旧服务端可能公开这些记录。回滚必须先停止评论读取，并将私密记录隔离或恢复到迁移前备份；不要直接删除隐私字段。

不支持把含私密记录的数据交给其他存储后端或忽略 `_privateViewer` 的自定义模型读取。

## 发布流程

`.github/workflows/release-server.yml` 只在推送 `v*` 标签时触发，进一步校验版本格式，例如 `v1.41.6-seiun`。日常分支推送不会发布镜像；普通测试工作流仍可运行。原有 npm 和 Docker Hub 发布路径在本 fork 中不运行。

确认代码已审查并提交到准备发布的提交后，手动创建、推送一个未使用的标签。例如以下命令仅用于将来的正式发布：

```bash
git tag -a v1.41.6-seiun -m "Private replies: first fork release"
git push origin v1.41.6-seiun
```

`main` 与上游 `main` 保持完全一致；定制代码保存在远端 `dev`，默认分支为 `dev`。标签从经过验证的 `dev` 提交创建。不要重用已经发布的版本标签。

Actions 会完成依赖安装、测试、管理后台／API／客户端构建，启动镜像检查静态资源，然后发布 `linux/amd64` 和 `linux/arm64` 镜像：

```text
ghcr.io/zhangyxxyz/waline:v1.41.6-seiun
```

同时附带提交 SHA 标签。没有自动更新的 `latest` 标签。工作流摘要会列出镜像 digest，1Panel 可使用 `ghcr.io/zhangyxxyz/waline@sha256:...` 精确锁定一次构建。

发布使用仓库自身的 `GITHUB_TOKEN` 和 `packages: write` 权限，不需要 Docker Hub 密码。首次使用需确认 fork 的 Actions 已启用；首次发布后的 GHCR 包若为私有，需要将包设为公开，或者在 1Panel 配置具备 `read:packages` 权限的拉取凭据。

## 1Panel 与博客接入

服务器只拉取镜像，无需在那里编译。继续使用现有 1Panel 编排，修改 Waline 服务的 `image`，保留数据库、OAuth、域名、反向代理和端口配置。容器仍监听 `8360`，数据库继续使用现有 `hexo_blog`，数据库密码不要放进 Dockerfile 或工作流。

镜像以 `node` 用户运行。如果现有编排挂载自定义文件或目录，需要确保该用户能读取配置、写入运行目录；不要覆盖镜像内的整个 `/app`。

镜像包含同一提交构建的三份资源：

```text
/assets/fork/admin.js
/assets/fork/waline.js
/assets/fork/waline.css
```

管理后台默认使用镜像内的 `admin.js`。如果旧编排设置了 `WALINE_ADMIN_MODULE_ASSET_URL` 指向官方 CDN，应改为 `/assets/fork/admin.js`。博客要使用本 fork 的客户端 JS/CSS，才会出现私密回复入口；仅换服务端镜像不会自动替换博客已打包的官方客户端。也可以把本次构建的客户端作为博客构建依赖一起锁定。

资源允许跨域加载，评论 API 仍沿用现有域名与 localhost 来源规则。此阶段没有修改博客接入，也没有部署到服务器。

## 验证与限制

使用仓库声明的 Node / pnpm 版本。Windows 下后台构建已改为通过 `cross-env` 设置环境变量。

```bash
pnpm exec vitest run
pnpm run build
```

私密回复集成测试运行真实 HTTP 鉴权、控制器、MySQL 存储适配器和 WHERE 编译器，使用独立的内存 SQL 数据库执行查询，不连接生产库。它覆盖访问角色、数量／分页、RSS、后台导出、写入、修改与删除限制。它不替代上线前对实际 MySQL 5.7 备份副本执行迁移的验收。

本机已检查打包依赖、启动打包后的服务端、读取三份资源及工作流静态校验。本机没有 Docker，首次 Actions 的容器构建与启动检查仍是正式发布前的验证步骤；调试用的旧标签已清理；当前发布暂停，服务器尚未升级。

## 存储和工作流清理

发布工作流名称为 `Publish @seiun/waline`。只接受 `vX.Y.Z-seiun` 标签；手动重试也必须选择对应标签，普通分支不能发布。后续版本递增版本号，不追加发布尝试次数。

镜像直接构建并上传 GHCR。成功后创建正式 GitHub Release，记录镜像标签和 digest。本流程没有跨任务文件传递，不创建临时 Release 草稿，也不上传 Actions 构建记录。保留 GHA 构建缓存用于加速，仓库缓存上限维持 10 GB；缓存与 Artifacts 使用独立额度，不在每次发布后清空。临时构建数据在 runner 内清理，runner 结束后销毁；最终 GHCR 镜像和正式 Release 保留。

`Delete old workflow runs` 每周日北京时间 08:00 清理：每个工作流保留最近 6 次运行，且保留所有不足 30 天和仍在运行的任务。手动运行默认仅预览；修改清理脚本触发的运行也仅预览。删除历史运行不会删除正式 Release 或 GHCR 镜像。

发布缓存按版本分组：新镜像成功推送并确认新缓存索引存在后，删除旧版本的 Docker 构建缓存，保留当前版本完整的索引与所有层。构建失败不清理上一版本缓存。发布任务串行执行，避免相互删除缓存；pnpm 测试缓存独立管理。
